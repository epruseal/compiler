# LLM 시행일 판단 기록

이 문서는 compiler#2에서 한 일, 부딪힌 문제, 결과와 사례를 기록한다. 판단 규칙의 정본은 정책 문서 `docs/llm-date-judgment.md`다. 작업 정본과 결정 원문은 [compiler 이슈 2](https://github.com/epruseal/compiler/issues/2)다. 파서 규칙의 예외와 사례는 `docs/enforcement-date-exceptions.md`(compiler#1)가 정본이다. 이 문서는 LLM 판단의 사례와 측정의 정본이다.

## 상태와 판정

- 판단 실행기, 원장, 대기열 생성기, 정책 문서, 사용자 결정 보호 목록은 구현했다(브랜치 `issue2-llm-date-judgment`).
  - 구현 뒤 필수 채널과 새 컨텍스트 실행 채널의 검증을 다섯 회차 받았고 마지막 판정은 둘 다 PASS다.
- compiler 통합(브랜치 `issue2-llm-integration`, compiler#1 PR 4 위)은 구현했다. `--llm-ledger`를 준 시행일 모드에서만 원장의 1단계 채택분을 쓴다. 적용된 판본은 status `llm`, frontmatter, 커밋 제목 표지 "(LLM 판단)"으로 구별된다.
  - 옵션을 주지 않은 출력은 compiler#1 PR 4(c5615c6)와 같다. 재현: 같은 입력과 argv로 두 바이너리를 돌려 Git 객체와 refs, manifest, 날짜 색인을 비교한다.
  - 시행일 모드 판본 커밋에는 기본 모드와 같은 식별 줄이 붙는다(`user-enforcement-mst-trailer-20261117`). 그래서 시행일 모드 출력과 c5615c6 출력은 그 줄만 다르다.
  - cli-tools 표시는 브랜치 `issue2-llm-date-display`(cli-tools PR 3 위)에 있다.
  - 구현 뒤 검증과 PR은 아직이다.
- 1단계(파서가 정하지 못한 판본의 판단)는 끝났다. 생성 저장소에는 아직 반영하지 않았다.
- 2단계(파서가 XML 시행일자 없이 정한 판본의 교차 확인)는 시범 500건에서 멈췄다(`user-stage2-stop-20261117`). 시범의 불일치는 1건이다. 나머지 후보는 돌리지 않으며 원장의 시범 결과는 그대로 둔다.
- LLM 판단은 법적 효력의 판정이 아니다. 원문 문장을 읽어 날짜를 고르고, 기계 검사가 그 문장이 원문에 있는지만 확인한다.

## 사용자 결정과 리드 재정

- `user-llm-remaining-judgment-20261116`(A.a1, B.B2, C.맡김): 파서 규칙은 compiler#1 r25c에서 멈춘다. 파서가 정하지 못한 판본은 LLM이 판단한다. XML 시행일자 없이 파서가 정한 판본은 LLM이 교차 확인하고 날짜가 다르면 미해결로 돌린다. LLM 판단은 구별해 표시하고 따로 저장한다.
- `lead-user-decision-protection-20261116`: 판본을 지목해 날짜나 결과를 정한 사용자 결정의 판본 20개는 보호한다. LLM이 판단하지 않는다. 목록은 `git-writer/data/llm-protected-revisions.json`이다.
- `lead-compiler2-check-contract-20261116`: 기계 검사는 출처만 확인한다. 인용이 원문에 있다, 같은 줄 인용 부호 쌍 안에 있지 않다, 날짜가 인용 안에 있고 달력상 유효하다, 시행 동사가 서술어 위치다, 상대기간과 라벨 날짜를 계산하지 않는다. 인용 문장이 이 판본의 시행일 문장인지는 LLM이 판단하고 정확도로 잰다.
- `user-compiler2-phase1-20261116`: Sonnet 5.5 기본 effort로 1단계만 실행한다(약 3,585회).
  - Q2, Q8, Q6: LLM은 문장에 적힌 날짜만 채택한다. 기간 계산과 사본 선택을 하지 않는다. 교차 확인에서 날짜 없는 시행 문장만 찾으면 불성립으로 두고 파서 날짜를 유지한다.
  - Q4: 일일 수집 스크립트는 고치지 않는다. 대기열은 수집 뒤 사람이 만든다.
  - 긴 부칙 발췌는 두 조건으로 수용했다. 발췌가 부칙 제목 구역을 보존해야 하고, 기계 검사가 원문 전체에서 인용을 확인해야 한다.
- `user-compiler2-shunt-path-20261116`: 실행 환경이 정한 사용자 구독 게이트웨이 경유를 인정한다. 금지하는 것은 유료 API 키(`ANTHROPIC_API_KEY`)다.
- `lead-compiler2-line-end-20261116`: 줄 끝은 문장 끝이 아니다. 2026-11-09 사용자 결정(줄 끝의 "다", "함"을 문장 끝으로 보지 않는다)과 같다.
- `lead-compiler2-f3-20261116`: 원장 policy와 다른 모델, effort, 프롬프트로는 명시 인자(`--replace-policy`) 없이 실행하지 않는다.
- `lead-compiler2-a2-a3-20261117`: 직전 멈춤과 다른 키 묶음에서 멈춘 실패는 실패 수에서 뺀다. 같은 키 묶음에서 다시 멈추면 뺀 실패까지 다시 센다. 세 번째 같은 멈춤 뒤에는 날짜 없는 `failed` 항목으로 남기고 건너뛴다. 유료 API 키 거부는 모든 호출 경로에 건다.
- `user-compiler2-phase2-pilot-20261117`: 2단계는 시범 약 500건(상한 520회)만 먼저 돌린다.
- `user-docs-living-record-20261117`: 이 문서를 두고, 새 예외와 발견이 생기면 고쳐 push한다.
- `user-stage2-stop-20261117`: 2단계는 시범 500건에서 멈춘다. 나머지 후보는 돌리지 않는다. 전체 실행의 부하(약 30시간)에 비해 바뀌는 판본이 적다(시범 불일치 1/500).
- `lead-c2-b3-strict-20261117`: B3 비교를 줄이지 않는다. 미적용 수를 보고한다.
- `lead-c2-baseline-20261117`: 옵션 비회귀의 기준선은 c5615c6에서 직접 빌드한 바이너리의 출력이다.
- `user-enforcement-mst-trailer-20261117`: 시행일 모드 판본 커밋 메시지에 기본 모드와 같은 식별 줄을 더한다. 자치법규는 "자치법규ID:"와 "자치법규일련번호:", 행정규칙은 "행정규칙일련번호:"와 "행정규칙ID:", 법령은 "법령MST:"다. 과거본을 일련번호 줄로 찾는 소비자가 시행일 모드 출력에서도 깨지지 않게 한다. 날짜 스냅샷 커밋은 바꾸지 않는다.
- `lead-c2-integration-contract-20261117`: compiler 통합에서 LLM 원장은 compiler#1 공유 승인 선택 지점의 두 번째 승인 출처다. 사용자 결정 승인과 같은 범위 규칙(B2), 귀속 조건(B3, 판단 때 파서 결과와 지금 파서 결과가 같을 때만 적용), 관문 정책, 소비 증거를 그대로 받는다.
- `user-c2-b2-llm-20261117`: LLM 인용에 B2를 적용할 때 인용 자신의 절은 비교에서 뺀다. 구역 안의 다른 시행 문장은 outcome별로 같은 날짜인지 판정한다. 명시 날짜는 같은 명시 날짜, 공포일은 "공포한 날"이나 공포일과 같은 명시 날짜, 라벨 날짜는 "공포한 날"이다. 날짜를 읽을 수 없는 다른 시행 문장은 보류 사유다.
- `user-c2-proviso-357-20261117`: LLM이 단서 있음으로 판단한 채택분 가운데 단서가 "다만"이나 "단,"으로 시작하는 것만 보류한다. 그 밖의 단서 판단(예: "시행하되 ~부터 적용한다")은 날짜를 막지 않고 근거로만 남는다. 이 결정 때의 수는 1단계 채택분 633건 가운데 357건 보류, 276건 적용이다(2026-11-17 원장 기준).
- `user-c2-quote-proviso-hold-20261117`: 파서가 LLM 인용 자신의 절에서 단서를 읽으면 보류한다. 파서의 단서어에는 공백 뒤 "단"도 든다. 인용 자신의 절은 B2의 같은 날짜 비교에서만 빠지고 단서 검사에서는 빠지지 않는다. 인용 자신의 절은 구역 좌표에서 절의 시작이 인용 일치 구간 안에 드는 읽힌 절이다.
- `user-c2-llm-repeal-no-20261117`: LLM 날짜를 받은 폐지 판본은 확정 폐지 뒤 부활 규칙의 확정 폐지로 쓰지 않는다. LLM 날짜가 다른 판본의 상태를 바꾸지 않게 하기 위해서다.
- `user-heading-check-keep-20261117`: 다음 판본 라벨 검사(section_not_later_revision)는 고치지 않는다. 제목 줄에 붙은 단서 날짜로 탈락한 S-HEADING-LINE 부류는 미해결로 남긴다. 과잉 거부는 잘못된 날짜를 내지 않는 보수 방향이다.

## 설계와 검증에서 부딪힌 문제

각 항목은 무엇이 틀렸는지, 어떤 반례로 드러났는지, 어떻게 고쳤는지를 적는다.

### P-PREDICATE: 서술어 어미의 열린 집합

- 문제: 첫 구현은 "시행한다" 뒤에 오면 안 되는 글자(는, 고, 면)를 금지 목록으로 막았다. 다음 꼴이 검사를 통과했다.
  - "이 조례는 2012. 1. 1.부터 시행토록 한다는 점을 고려한다."
  - "시행하였다면", "시행한다던 계획"
- 첫 수정: 금지 목록에 "던"을 더했다. 그러자 "시행한다며", "시행된다지만", "시행한다니"가 통과했다. 인용 연결 어미는 열린 집합이라 금지 목록으로 닫을 수 없었다.
- 최종: 종결형(다, 함, 됨, 킴으로 끝나는 어미) 뒤 글자를 허용 목록으로 바꿨다. 허용하는 것은 마침표, 쉼표, 세미콜론, 닫는 부호, 칸 끝뿐이다.

### P-LINE-END: 줄 끝을 문장 끝으로 본 회귀

- 문제: 허용 목록에 줄 끝을 넣었다.
- 반례: 강제 줄바꿈 본문 "상위 법령이 2009. 6. 27.부터 시행됨" + 줄바꿈 + "에 따라 관련 조문을 정비함."이 채택됐다. 첫 구현이 거부하던 꼴이다.
- 결정: 리드 재정(줄 끝은 문장 끝이 아니다)으로 줄 끝 허용을 뺐다. 마침표 없이 줄이 끝나는 시행 문장은 미해결로 남는다.

### P-MUTATION: 시험이 잡지 못한 변이

- 검증 방법: 실행 채널이 검사 코드를 하나씩 무력화했다(역변이). 그때도 시험이 통과하는지 봤다.
- 1차: 변이 75개 가운데 동작을 바꾸고도 살아남은 것이 34개였다.
- 그 뒤에도 같은 원인이 되풀이됐다. 원인은 검증자 반례를 그대로 옮기지 않고 비슷한 시험을 새로 쓴 것이었다. 되풀이된 변이는 두 가지다.
  - 재판단 대상 수의 조건.
  - 대기열 낡은 항목 집합의 조건.
- 리드 재정으로 반례 입력을 그대로 시험으로 옮겼다. 커밋 전에 작성자가 변이를 직접 넣어 시험이 실패하는지 확인하게 했다.
- 마지막 회차 결과: 변이 163개 가운데 동작이 다른 생존 0개. 남은 생존 6개는 판정이나 날짜를 바꾸지 않는 진단 값과 경고 수의 차이다.

### P-STOP-RULE: 연속 실패 규칙이 대상별 상한을 무력화

- 처음 규칙: 연속 5번 실패로 멈춘 실행의 실패는 공통 원인(사용 한도, 로그인)으로 보고 대상별 수에서 뺐다.
- 문제: 늘 실패하는 대상이 다섯 넘게 이어지면 매 실행이 같은 자리에서 멈췄다. 그 대상들은 상한에 닿지 않아, 뒤 대상이 영구히 판단되지 않았다.
- 재정 뒤 규칙: 직전 멈춤과 같은 키 묶음에서 다시 멈추면 센다.
- 검증된 동작: 1-3회 실행은 같은 다섯 대상에서 멈췄다. 4회 실행은 그 다섯을 `failed` 항목으로 남기고 다음 대상을 불렀다.

### P-PAID-KEY: API 키 거부 범위와 게이트웨이 경유

- 정답 표본 측정의 호출 320건은 실행 환경의 게이트웨이를 거쳤다. 자식 프로세스가 셸 환경의 게이트웨이 변수를 물려받았기 때문이다. 사용자는 이 경로를 구독 경로로 인정했다.
- 유료 API 키 거부는 처음에 `run`에만 있었다. 지금은 공유 지점 `call_cli`에 있어 `run`, `one`, 측정 스크립트가 모두 거부한다.

### P-EXCERPT: 긴 부칙 발췌의 경계

- 누적 부칙이 300만 자가 넘는 판본(2114201)은 호출이 "Prompt is too long"으로 실패했다.
- 그래서 마지막 8개 구역과, 제목에 이 판본의 공포일이나 공포번호가 든 구역만 싣는 발췌를 더했다.
- 문제: 발췌가 여전히 상한을 넘을 때의 대체 경로가 끝에서 글자 수로 잘랐다. 이 경로는 구역 가운데와 제목 줄을 잃을 수 있었다. 사용자 수용 조건(제목 구역 보존)을 어긴다.
- 수정: 앞 구역을 통째로 버리게 고쳤다. 기계 검사는 발췌가 아니라 원문 칸 전체를 읽는다.

### P-JOURNAL: 다바이트 문자 안에서 잘린 journal 줄

- 문제: journal을 파일 전체 UTF-8로 복호화했다. 그래서 마지막 줄이 한글 3바이트 가운데서 잘리면 정리 단계가 예외로 멈췄다.
- 수정: 바이트 줄 단위로 읽게 했다. 잘린 줄은 버리고 실행 보고에 `journal_cut_line_at_start`로 알린다.

## 정답 표본 결과

- 정답 표본 90건은 사용자 결정과 리드 기록이 결과를 정한 판본이다. LLM 호출 전에 고정했다.
- 날짜 결과 80건에서 Opus 5.5와 Sonnet 5.5는 79건이 맞고 잘못 채택이 1건이다. 수치와 판은 아래 측정 기록에 있다.

### G-STALE-ADDENDUM: 이전 판본 부칙의 날짜 채택 (2200000095587)

- 원천: 행정규칙 2200000095587. 자기 부칙이 없는 일부개정 판본이다.
- 원문: 부칙 칸의 유일한 구역에 "이 예규는 1988. 5. 4.부터 시행한다."가 있다. 이 구역은 이전 판본의 부칙이다.
- 기대: 날짜 없음(conditional_or_external 또는 insufficient_text).

  - 한 판본의 사본 가운데 하나라도 불일치면 날짜 있는 사본을 모두 거둔다(관문과 llm-copy-mismatch와 같은 방향). 지금 원장에서는 발동하지 않는다.

  - 3회차 검증도 같은 쟁점으로 FAIL이었다. 불일치 행의 이동은 부모, 변경 종류, SHA 칸, inline 폐지 행처럼 커밋 그래프의 새 변형을 계속 만들었다. 그래서 리드 재정 `lead-c2-v35-round4-state-compare-20261117`은 불일치 행이 든 실행의 비교 단위를 커밋에서 상태로 바꿨다. 행(SHA 칸과 순위를 지운 manifest 행)과 snapshot 날짜별 tree, 저장소 밖 진단 파일을 비교한다. 커밋 그래프의 모양은 숫자로만 보고한다. 공포일자 조회에서 불일치 판본이 selected로 나오면 cli는 status와 관계없이 두 후보를 보인다.
  - 4회차 검증에서 확인한 사실: 날짜 색인 파일 머리의 `snapshot_date`는 그 identity를 마지막으로 다시 쓴 snapshot의 날짜다. 불일치 행이 날짜 묶음을 옮기면 그 identity 파일의 이 값이 이후 snapshot에서 갈린다. 리드 재정 `lead-c2-v35-round5-20261117`으로 불일치 identity 파일은 이 칸을 지우고 비교한다. 불일치 행을 지워 비게 된 파일과 파일 없음은 같다고 보지 않고 멈추고 보고한다.
  - 일치 판본의 받아들임 기준은 `lead-c2-v35-accept3-fix-20261117`이다: 본문 경로, 본문 blob, 커밋 메시지, status, 날짜, reason이 같고, 날짜 색인과 manifest의 차이는 `date_evidence.llm_cross_check` 키 안에만 있다. 날짜 색인 파일이 시행일 모드 Git tree 안에 있으므로 tree 동일은 기준으로 쓸 수 없다.

## 측정 도구의 한계

- 1단계 대상의 전이 근거: 1단계 대상은 r25c3 시제품 manifest로 정했다.
  - compiler#1 이식본의 manifest가 덮는 범위 1,189건은 직접 대조했고 차이가 0이다.
  - 나머지 자치법규 2,285건은 두 증거를 이은 전이 근거다. 첫째, compiler#1 모집단 12실행에서 시제품 두 판의 차이는 세 승인 판본뿐이다. 둘째, 이식본 5실행의 manifest가 시제품과 바이트로 같다.
  - 이식본 전체 manifest가 생기면 대상 집합을 다시 대조한다.
- 정답 표본은 90건이다. 1단계의 채택 2,055건의 정확도를 직접 재지 않았다. 표본 오류율을 1단계 전체에 옮겨 적지 않는다.
- 분포의 outcome은 LLM의 분류다. "귀속 불명"이나 "조건" 같은 보류 사유는 사람이 확인하지 않았다.
- S-HEADING-LINE 부류의 건수는 세지 않았다.
- 부분 코퍼스 실행(compiler#1 모집단의 base7 계열)에서는 다음 판본이 전체 코퍼스와 달라 next-revision-changed가 많이 난다. 설계상 코퍼스에 따라 갈리는 결과이므로 원장 대조는 전체 코퍼스 실행으로만 낸다.

## 안전한 원문 재현

원자료 캐시를 읽기만 한다. 선택한 판본의 XML 원문은 `docs/enforcement-date-exceptions.md`의 "안전한 원문 재현" 절 명령으로 조회한다. LLM 판단과 검사 결과는 운영 폴더의 원장에서 조회한다.

```sh
OPS=/path/to/llm-date-judgment   # 운영 폴더
DATASET=ordinances               # ordinances 또는 admrules
REV=744550
python3 -I - "$OPS" "$DATASET" "$REV" <<'PY'
import json, pathlib, sys
ops, dataset, rev = pathlib.Path(sys.argv[1]), sys.argv[2], sys.argv[3]
doc = json.loads((ops / 'ledger' / f'{dataset}.json').read_text(encoding='utf-8'))
for e in doc['entries']:
    if e['key']['revision'] == rev:
        j = e.get('judgment') or {}
        print(e['kind'], e.get('adoptable'), e.get('date'), j.get('outcome'), j.get('basis_quote'))
        print({k: v for k, v in (e.get('checks') or {}).items() if v is False})
PY
```

기계 검사만 다시 돌리려면 `python3 -I tools/llm-date-judgment/judge.py one`을 쓴다. 이 명령은 LLM을 부르므로 측정 목적일 때만 쓴다. 정답 표본의 재채점은 저장된 응답으로 `python3 -I tools/llm-date-judgment/measure/gold_run.py score --out <측정 폴더>`를 쓴다. 이 명령은 LLM을 부르지 않는다.
